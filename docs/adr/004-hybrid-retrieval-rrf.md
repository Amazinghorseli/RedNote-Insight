# ADR-004: 四层混合检索管道（向量 + BM25 + RRF + CrossEncoder）

- **状态**：✅ 已采纳
- **日期**：2025-06
- **决策者**：项目作者

---

## 背景

RAG 系统的核心瓶颈在检索。如果检索到的文档不相关，后续 LLM 生成的报告再漂亮也没用。

小红书笔记的搜索场景天然需要两种能力：
- **语义理解**：用户搜"便宜好用的收纳盒"需要找到"平价收纳神器"（语义相似但用词不同）
- **精确匹配**：用户搜"磁吸感应灯"需要精确命中品牌名、品类名

单一检索方式无法同时满足这两种需求。

## 决策

**采用四层检索管道：向量检索 + BM25 关键词检索 → RRF 融合 → CrossEncoder 重排序。**

```
① 向量检索（BGE-M3 Embedding） → 25 篇（语义相似）
② BM25 检索（jieba 分词）       → 25 篇（关键词匹配）
③ RRF 融合                      → Top-10
④ CrossEncoder 重排序            → 过滤 < 0.1 → 保留高相关
```

### RRF 公式

```
rrf_score = 1.0 / (60 + rank + 1)
```

常数 60 是 RRF 论文推荐值。让排名衰减曲线平滑——第 1 名权重约是第 60 名的两倍。太小让 top 文档权重过高，太大让权重趋于平均。

### 为什么 CrossEncoder 而非 LLM-as-Judge

| | LLM-as-Judge | CrossEncoder |
|---|---|---|
| **原理** | 生成 token 判断 | 直接输出分数 [0,1] |
| **速度** | ~500ms/篇 | ~50ms/篇 |
| **成本** | 每次调用计费 | 一次 batch 调用 |

## 后果

**正面：**
- 语义理解 + 精确匹配互补，一篇笔记如果同时在向量和 BM25 排名靠前，RRF 会显著提权
- CrossEncoder 比 LLM-as-Judge 快 10 倍，且一次 API 调用处理所有文档

**负面：**
- 四层管道增加了检索延迟（约 455ms：向量 200ms + BM25 5ms + RRF <1ms + CrossEncoder 250ms）
- CrossEncoder 依赖外部 API（SiliconFlow），网络抖动会影响稳定性

**缓解措施：**
- 对 CrossEncoder 分数设 0.1 阈值——不过滤可能有用的微弱相关文档，同时剔除明显无关噪音
- 基于分值分布观察确定阈值：不相关文档通常 < 0.05，微弱相关 0.05-0.1，明显相关 > 0.15

## 备选方案

1. **纯向量检索** — 对品牌名、型号等精确术语召回率低
2. **纯 BM25** — 无法理解语义相似，搜索"好用"找不到"推荐"
3. **LLM-as-Judge 重排序** — 更"聪明"但每篇 ~500ms，10 篇就是 5 秒，用户无法接受

## 面试话术

> "'磁吸感应灯哪个品牌好'——'磁吸感应灯'需要精确匹配，'哪个品牌好'需要语义理解。两者缺一不可。向量抓语义、BM25 抓术语、RRF 无缝融合、CrossEncoder 做最后把关。四层管道的每一层都有明确的失败模式和备选方案。"
